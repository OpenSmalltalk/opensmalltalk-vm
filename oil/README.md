# Oil JIT: `ProfilingCogit` and Native Runtime

`ProfilingCogit` (a subclass of `StackToRegisterMappingCogit`) is the VM integration tier of Oil, the optimizing JIT for the 64-bit Spur Cog VM. It adds lightweight trip counters to baseline code, queries inline caches for type feedback, drives the Oil optimizing compiler (`OilInliningCompiler` -> `OilLoopOptimizer` -> `OilFullCompiler`), manages the Oil selector table and deoptimization metadata, and implements the bailout/deoptimization runtime in `CoInterpreter`.

## Files and Load Order

To generate the 64-bit Spur Oil VM (`src/spur64.oil`), file into `Spur64VMMaker.image` in this order:

1. `oil/oil-m1-profiling-cogit.st` — `ProfilingCogit` class definition, trip counters at loop back jumps, `CoInterpreter>>ceOilTrip:` (which compiles the hot home method with Oil, see `oilAutoCompile:receiver:`), `primitiveOilMonomorphicTarget`, and `VMMaker class>>generateSqueakSpurCogOil64VM`.
2. `image/oil/OilInstructionConstants.st` — shared pool of 32-bit linear IR instruction opcodes.
3. `image/oil/OilConstants.st` — shared pool of descriptors, tags, limits, and runtime constants (imports `OilInstructionConstants`).
4. `image/oil/OilBytecodeScanner.st` — `OilBytecodeDescriptor` and `OilBytecodeScanner`.
5. `image/oil/OilCompiler.st` — `OilInliningCompiler` (Pass 1 and `#pipe` hook).
6. `image/oil/OilCompilerBackend.st` — `OilInliningCompiler` (Pass 3 native code generation).
7. `image/oil/OilCompilerPass2.st` — `OilLoopOptimizer` (Pass 2 loop optimizer) and `OilFullCompiler`.
8. `oil/oil-m3-native-backend.st` — `ProfilingCogit` Oil driver (`oilCompile:receiverClass:`, `oilGenerate:`), deoptimization metadata (`fillMetadata:cogMethod:`), `CoInterpreter>>ceOilDeoptimize:`, selector table, invalidation on selector flush (`unlinkSendsOf:isMNUSelector:`), autonomous compilation on trips (`oilAutoCompile:receiver:`, `oilUnhookBaselineCodeOf:`), and primitives (`primitiveOilCompile`, `primitiveOilSetColdSelectors`, `primitiveOilSetParameter`, `primitiveOilMethodInfo`, `primitiveOilLastCompilation`), and the debugging primitives (`primitiveOilContexts`, `primitiveOilDeoptimize`, `primitiveOilMetadata`; see `image/oil/OilDeoptMetadataReader.st`).
9. `oil/oil-m7-specialization.st` — method-level multi-specialization: the specialization table, the dispatch at the no-check entry of baseline methods (`ProfilingCogit>>compileEntry`), direct linking of monomorphic sends (`linkSendAt:in:to:offset:receiver:`), the interpreter's entry (`CoInterpreter>>activateNewCogMethod:inInterpreter:`), and `primitiveOilSpecialize`, `primitiveOilSpecializations`.

Then run `VMMaker generateSqueakSpurCogOil64VM` and build with `building/linux64x64/squeak.cog.spur/build.oil/mvm` (produces `products/sqcogspur64linuxht.oil/squeak`).

## Key Runtime Mechanisms

- **Trip counters**: 32-bit counters (initialized to `OilInitialCounterValue`, 8191) are placed only at loop back jumps (`genJumpBackTo:`), taken from a 4 KB ring buffer in the VM's static data (Milestone 12). At each site the counter is decremented; when it reaches zero (once: it then goes negative), the site invokes `ceOilTripTrampoline` with `SendNumArgsReg` set to the kind of site (`OilTripBackJump`, the only kind). The trampoline calls `CoInterpreter>>ceOilTrip:`, which identifies the outer home method, compiles it with Oil for the class of its receiver and installs the Oil code for its next activations (`oilAutoCompile:receiver:`: the baseline code moves to a copy of the method, which its running activations finish in, `oilUnhookBaselineCodeOf:`; a method Oil fails to compile is disqualified), then returns directly to machine code. `primitiveOilSetParameter` (parameter 19) turns autonomous compilation off.
- **Selectors**: the value selectors, `bitXor:`, the methods of the byte scans and the default cold selectors (`OilInliningCompiler class>>defaultColdSelectors`, never inlined) are recognized by name in the VM; `primitiveOilSetColdSelectors` replaces the cold selectors with the image's Array of Symbols (a GC root).
- **Entry points**: `primitiveOilCompile` runs `oilCompile:receiverClass:` (Pass 1) while baseline inline caches are still linked, frees the baseline `CogMethod` and divorces its frames, and runs `oilGenerate:` (`#pipe` + Pass 3).
- **Deoptimization metadata & `ceOilDeoptimize:`**: An Oil `CogMethod` stores the oop of its pinned metadata tagged with `1` in its `counters` field (`isOilMethod:`). The metadata is a hidden object of `CompiledMethod` format (Milestone 11): a literal frame, which the garbage collectors trace like a method's (the root method, the inlined selectors, the methods of the inlined frames, CompiledBlocks, classes, constants), then little-endian bytes: a header, fixed-size frame and virtual object records with 2-byte descriptors, the spill offsets of the spilled registers only, a site table, and site records whose virtual states use 1-byte descriptors for registers holding their own value and for nil (see the `OilMD*` constants in `OilConstants`). It is about 90% smaller than the pointer `Array` of Milestones 1 to 10 (e.g. 392 instead of 4464 bytes for `sumScores:`). On a failed guard or check, the deopt stub passes the site index to `ceOilDeoptTrampoline` -> `CoInterpreter>>ceOilDeoptimize:`, which either unforwards a forwarded receiver/argument and resumes machine code in place, or reconstructs the interpreter frame stack (rematerializing any virtual closures and temp vectors) and continues in the interpreter. After `OilDisqualifyDeopts` deoptimizations, the Oil method is freed and disqualified from future Oil compilation.
- **Oil selector table**: Sends of selectors from inlined methods that are not among the root method's literals are indexed via `oilExtraSelectors` (`OilExtraSelectorBase + k`) and dereferenced by `ceOilDereferenceSelectorIndex`. When a selector is flushed (`unlinkSendsOf:isMNUSelector:`), any Oil method that inlined that selector is discarded if not currently active on the stack.
- **Method-level specialization** (`primitiveOilSpecialize`): a method may have up to `OilMaxPICCases` (5) Oil versions, one per receiver class, besides its baseline code, which runs every other receiver (the sixth case, as in a closed PIC). The Oil code of the specialization of method M for class C is the machine code of a copy M_C of M, so every CogMethod keeps its own CompiledMethod (freeing, compaction and contexts are unchanged); the specialization table (`oilSpecializations`, a GC root, `OilMaxSpecializations` entries M, class tag, M_C, C) records them; an entry is live while M_C has Oil code, C still has the tag and M_C still has M's literals and bytecodes. M's baseline code dispatches on the receiver's class tag at its no-check entry, where linked sends (after the inline cache check), super sends and the interpreter enter: for class C it jumps to the no-check entry of M_C's machine code, read through M_C's header (the CogMethod's address while it has machine code, a SmallInteger otherwise), so freeing or moving the Oil code needs no patching. Monomorphic sends of receivers of class C are linked directly to M_C's Oil code. Voiding M's machine code in place (`voidCogVMState`, `flushCache`) or becoming M drops its entries; at code compactions copies take M's usage count and the Oil code of dead entries is freed. A deoptimization disqualifies the root method M.
- **Code zone and eden sizes**: `ProfilingCogit>>defaultCogCodeSize` defaults to 4 MB, and `CoInterpreter>>checkImageHeaderLoad` clamps the code zone to at least 4 MB (baseline and Oil methods share ample room without premature code compactions) and eden to at least 16 MB (Oil code allocates; an allocation beyond the scavenge threshold deoptimizes).
